# ADR-0077: Personal usage dashboard with built-in email variable and folder-level RBAC

**Status:** Accepted
**Date:** 2026-07-03
**Deciders:** @stephane-segning

## Context

End users of the AI gateway (LibreChat users) have no way to see their own
token usage and cost. The existing per-user dashboard
(`per_user.py` / `envoy-ai-gateway-per-user`) is an admin-only tool: it
exposes a `user_id` query variable that lets the viewer select *any* user,
which is inappropriate for client-facing access.

We need a dashboard that each authenticated user can open to see *only their
own* usage, without being able to view other users data. The user has
read-only cluster access (no write/deploy), Grafana is stateless
(ADR-0023 — dashboards-as-code only), and all dashboards are generated via
the Python `grafana-foundation-sdk` and committed as JSON to git.

## Decision

Adopt **Option A: Grafana built-in email variable**. Create a new dashboard
(`my-usage`, uid `my-usage`) that uses the Grafana built-in
`${__user.email}` variable for per-user isolation. Every LogQL query
filters on `email="${__user.email}"`, so the dashboard only ever
shows data for the authenticated user.

The Loki `email` label is already promoted by Alloy from the JWT `email`
claim (see `docs/per-user-observability.md` label cardinality table).
It is 1:1 with `user_id` for human users. Grafana `${__user.email}`
is populated from the OIDC `email` claim by the existing `generic_oauth`
integration — no Grafana config changes are needed.

Unlike a URL variable, `${__user.email}` is a server-controlled built-in
variable — the viewer cannot change it via the URL or UI. Combined with
folder-level RBAC (Viewer cannot access Explore in Grafana OSS), this
provides a robust isolation boundary without Enterprise features.

The dashboard is generated by
`tools/dashboards/src/dashboards/envoy_ai_gateway/my_usage.py` and the
output JSON is committed to
`charts/observability-dashboards/files/envoy-ai-gateway/my-usage.json`.
It is deployed via the `observability-dashboards` Helm chart in a new
`my-usage` folder.

Folder-level RBAC enforces access control at the Grafana folder
level via the GrafanaFolder CR `spec.permissions` field. The `ai-gateway`
folder (admin dashboards) grants Admin=4 and Editor=2 only — Viewer is
intentionally omitted, denying read access to dashboards that show all
users data. The `my-usage` folder grants Admin=4, Editor=2, and Viewer=1,
so every authenticated user can view their own usage dashboard. Grafana
OIDC maps Keycloak roles: admin role to Grafana Admin, editor role to
Editor, everyone else to Viewer.

### Dashboard panels

1. **Total cost** (stat, USD)
2. **Total requests** (stat)
3. **Total tokens** (stat)
4. **Cost over time** (timeseries, stacked by model)
5. **Cost by model** (piechart)
6. **Tokens by model** (piechart)
7. **Requests by model** (piechart)
8. **Latency p50/p95** (timeseries)
9. **Usage by channel/azp** (piechart)
10. **Your account** (stat, shows display_name)

Variables: `azp` (query, multi-select), `model` (query, multi-select).
Both filter by `email="${__user.email}"`.

## Consequences

**Positive**
- Each user sees only their own data — no admin intervention needed.
- Dashboards-as-code pattern preserved (ADR-0023); no Grafana state.
- `${__user.email}` is a server-controlled built-in variable — users
  cannot change it to view others data.
- No Grafana config changes needed — `${__user.email}` maps to the
  OIDC `email` claim by default, and the `email` Loki label already
  exists (promoted by Alloy).
- Folder-level RBAC denies Viewer access to admin dashboards and to
  Grafana Explore (Viewer role cannot access Explore in Grafana OSS).
- No URL parameter needed — the dashboard works immediately for any
  authenticated user with Viewer access to the `my-usage` folder.

**Negative**
- Service account (SA) tokens have no `email` label (empty → no label).
  The my-usage dashboard is intended for human users (LibreChat), who
  always have email. SA traffic is visible in admin dashboards (which use
  `user_id`).
- Grafana OSS has no row-level security — a Viewer with access to a data
  source could theoretically query it directly. However, Viewers cannot
  access Explore in Grafana OSS, and the admin folder is denied to
  Viewers, so the practical attack surface is limited to the `my-usage`
  dashboard queries (which are server-controlled).

**Neutral / follow-ups**
- LibreChat integration: add a "View my usage" link in LibreChat
  navigation that opens the Grafana dashboard URL. No URL parameter
  needed — Grafana resolves `${__user.email}` server-side.
- Folder-level RBAC is implemented via GrafanaFolder `spec.permissions`.
  The `ai-gateway` folder restricts access to Admin and Editor only; the
  `my-usage` folder grants Viewer (view) to all authenticated users.

## Alternatives considered

- **Option B: URL-variable isolation (original approach)** — the initial
  implementation used a hidden constant variable `user_id` populated from
  the URL parameter `?var-user_id=<uuid>`. This was rejected because the
  variable was fully controllable via the URL — a Viewer who knows another
  user UUID could view their data by changing the URL parameter (IDOR).
- **Option C: `${__user.login}` with `login_attribute_path = sub`** —
  would map the Keycloak `sub` UUID to `${__user.login}` so it matches
  the `user_id` Loki label. Rejected because: (1) it requires a Grafana
  config change in `ai-helm-values`, (2) it changes every user displayed
  login from username to UUID, (3) GitHub issue #79328 reports edge cases
  causing login failures in some Grafana versions. The `email` approach
  achieves the same isolation with zero config changes.
- **Option D: Grafana auth proxy with per-user session** — would require
  configuring an auth proxy that maps SSO identity to a Grafana user.
  `${__user.email}` achieves the same result with less infrastructure
  by using the existing `generic_oauth` integration.
- **Option E: Separate dashboard per user** — rejected: does not scale;
  would require generating and deploying one dashboard JSON per user.
- **Reuse the admin `per_user` dashboard with a fixed variable** —
  rejected: the admin dashboard exposes `user_id` as an editable query
  variable, so a client-facing user could change it to view others data.
