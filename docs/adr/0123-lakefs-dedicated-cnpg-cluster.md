# ADR-0123: Give LakeFS its own dedicated CNPG cluster

**Status:** Accepted
**Date:** 2026-08-09
**Deciders:** @stephane-segning

## Context

Incident, `hetzner-prod`, 2026-08-08/09: LakeFS's HTTP API started returning
`repository not found` / auth errors and falling back to rendering its
first-run `/setup` page. Root cause: `lightbridge-main-db`, the CNPG cluster
in `converse` LakeFS's metadata KV store lives on per ADR-0085's decision #3
("new apps get a managed CNPG role + `Database` CR on the existing
`lightbridge-main-db` cluster instead of a dedicated CNPG cluster"), ran out
of Postgres connections: `FATAL: sorry, too many clients already` (SQLSTATE
53300). `max_connections` was left at the CNPG default (100), shared by 7
tenant roles (`repoauth`, `codeintel`, `grafana_ro`, `coder`, `lakefs`,
`mlflow`, `governance`), each with its own client-side pool, no PgBouncer in
front. LakeFS itself contributed a 25-connection default pool it never
needed (Stage 1 of this incident's fix caps it to 5).

Stage 1 of the incident fix (this repo, `charts/lightbridge-db`, and
`ai-helm-values` `lakefs-app.yaml`) restored service by raising
`max_connections`/memory on the shared cluster and capping LakeFS's own pool.
That does not fix the underlying coupling: LakeFS's data-versioning plane —
the system of record for every dataset commit — remains one connection-storm
on an unrelated tenant (`mlflow`, `coder`, `governance`,
`lightbridge-code-intelligence`) away from going unreadable again. None of
those tenants are LakeFS's operators or reviewers; a change to any of them
can take LakeFS down with no warning (CNPG reports `Cluster in healthy
state` throughout — it tracks replication/pod health, not per-tenant
connection saturation, so nothing alerted).

## Decision

Supersede ADR-0085 decision #3 **for LakeFS specifically** (decisions #1 and
#2 in that ADR — S3 backend, per-app auth strategy — are unaffected and
remain in force). Give LakeFS a dedicated CNPG cluster, `lakefs-main-db`, in
the `mlops` namespace (the same namespace as the rest of the LakeFS stack),
via a new `charts/lakefs-db` leaf chart of the `lakefs` App-of-Apps
orchestrator — mirroring the `lightbridge`/`lightbridge-db` pattern
(ADR-0019), not a variant of it. `lightbridge-main-db`'s `lakefs` managed
role, `lakefs` `Database` CR, and `lakefs-db-role` `ExternalSecret` are
removed (hard cutover — this repo's convention is to remove the old path in
the same change, not leave a dormant parallel one).

**Instance count: 3**, not the 2 that `lightbridge-main-db` and this repo's
other CNPG cluster otherwise use. This is a deliberate departure, not a
default: `lightbridge-main-db` is a general-purpose shared app database
where a 2-instance loss window is an acceptable, recoverable inconvenience
for its various tenants. `lakefs-main-db` is the sole system of record for
every dataset commit this platform's model-training pipelines depend on —
losing quorum here doesn't inconvenience one app, it makes the entire
data-versioning plane unreadable. A third instance keeps one standby in
reserve even after a single node loss, which two instances cannot. The extra
pod's CPU/memory/storage cost is small at this cluster's size (see sizing
below) and is judged worth it for that asymmetry.

**Data migration: none.** The owner confirmed current LakeFS data is
disposable ("we have no data yet, so we can safely destroy everything") and
hermetic-synthetic — the three dataset commits published before this
incident (`ds-document-recognizer`, `ds-document-detector`,
`ds-face-detector`) rebuild in ~1 minute each via the existing Argo
dataset-build workflows (`docs/playbooks/fixed-lakefs-dataset-workflows.md`
in `webank-models`). `lakefs-main-db` starts empty; those three commits
become unreachable on cutover and are regenerated by re-running the
workflows, not restored.

**Sizing**, deliberately not copied from `lightbridge-main-db`'s numbers:
this cluster serves exactly one client, LakeFS, with a hard-capped
5-connection pool (Stage 1). `postgresql.parameters.max_connections: "50"`
— generous headroom over 5 for `psql` debugging, the CNPG monitoring
exporter, and backup/migration connections, still small and well understood
for a single-tenant cluster. Memory: worst case with `work_mem` at Postgres's
4MiB default (unset here) is 50 × 4MiB ≈ 200MiB, plus per-backend base
overhead (≈50 × 2MiB ≈ 100MiB) and CNPG's own `shared_buffers` default
(128MiB) — call it ≈430MiB worst case. `resources.limits.memory: 1Gi` /
`requests.memory: 512Mi` covers that with real headroom without the
`lightbridge-main-db` pattern of setting requests so far below limits they
give no real signal. `storage.size: 2Gi` — LakeFS's KV data is refs/commits/
metadata (small keys and values), not the S3-resident object content the
repositories actually version, so this does not need to scale with dataset
size.

## Consequences

**Positive**
- LakeFS's failure domain no longer includes `mlflow`/`coder`/`governance`/
  `lightbridge-code-intelligence` or any future tenant added to
  `lightbridge-main-db`.
- `lightbridge-main-db`'s connection budget is freed of a tenant it never
  needed to carry, on top of Stage 1's fix.
- A 3-instance dedicated cluster gives LakeFS's data-versioning plane a
  stronger durability posture than it had as one of seven roles on a
  2-instance shared cluster with an unbounded/un-monitored tenant count.

**Negative**
- A second CNPG cluster to operate: its own `ObjectStore`/`ScheduledBackup`/
  `PodMonitor`, its own S3 backup credentials Secret, its own certificate/
  connection-string wiring in `charts/lakefs-secrets`. ADR-0083's original
  rationale for the shared-cluster pattern ("no new CNPG cluster to manage,
  no S3 backup credentials needed, fewer CRDs") is explicitly traded away
  here, for LakeFS only, because the durability argument for this
  particular tenant outweighs it.
- The historical LakeFS KV state (three dataset commits) is not migrated —
  see Data migration above. Acceptable per the owner's explicit sign-off
  that current data is disposable; would NOT be acceptable once real
  (non-synthetic, non-rebuildable) datasets are versioned in LakeFS.

**Neutral / follow-ups**
- If a future tenant on `lightbridge-main-db` needs the same isolation
  argument (a system of record whose loss is not a recoverable
  inconvenience), this ADR is the precedent to point to rather than
  ADR-0083's "prefer the shared cluster" default.

## Alternatives considered

- **Keep the shared cluster, just tuned (Stage 1 only).** Rejected as the
  *permanent* answer: Stage 1 fixes the immediate connection exhaustion but
  leaves LakeFS's data-versioning plane coupled to every other tenant's
  future connection behaviour indefinitely. Stage 1 stands on its own as the
  correct immediate mitigation; this ADR is the follow-up that removes the
  coupling instead of re-tuning around it forever.
- **Add a CNPG `Pooler` (PgBouncer) in front of the shared cluster instead.**
  Considered in Stage 1 and deferred there (see that PR): this cluster is
  shared by tenants this incident response has no evidence about w.r.t.
  session-level Postgres features transaction-mode pooling can break. Also
  doesn't address the actual problem — LakeFS's data would still be one
  connection storm away from unreadable, just with a different failure
  threshold.
- **2 instances, matching `lightbridge-main-db`.** Rejected — see Sizing/
  Decision above: the asymmetry in what's lost on a quorum failure (a
  general app database vs. the sole record of every dataset commit) justifies
  the extra instance here specifically, not as a new blanket default.
